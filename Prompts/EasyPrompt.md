# 概要要求

帮我用Python写一个小工具，名字叫“Easy Prompt”，运行在Windows 10 64位，下面是具体要求：

# 具体要求

## 布局要求

### 主页面

要求有一个主页面，大小默认1200x800px。主页面有边栏和当前界面，分别占1/8和7/8宽度。

#### 边栏

边栏垂直排列有可操作界面图标栏（上对齐）与设置图标（下对齐）。

##### 可操作界面图标栏

可操作界面图标栏从上到下分别是主功能界面图标（默认激活）和预设切换界面图标，具体图案自己想。

##### 设置图标

设置图标图案为齿轮。齿轮图标点击后在新窗口弹出设置栏。

#### 可操作界面

##### 主功能界面

操作界面从上到下分别是输入栏、提示栏和模型输出框。

输入栏（无标题）从左到右是两个输入框，分别宽度占母界面2/3与1/3，当内容超出可显示范围时显示滚动条并支持鼠标位置在界面内时使用滚轮进行滚动，左边标题“user prompt”，可输入user prompt；右边标题“system prompt”，可输入system prompt。

提示栏（无标题）从左到右分两栏，宽度分别占母界面1/4和3/4，左栏为计时器，无标题，显示当前状态【等待（等待用户输入或模型输出完毕）/已发送（已将消息发送给模型，等待回复）/错误（发送等待超时或出现其他错误）】；右栏为报错输出（不可编辑），无标题，默认为灰色的“报错输出”字样，当出现错误（等待超时/验证错误/API地址错误/其他）时显示简洁的报错信息。

模型输出框（不可编辑），标题“输出”，当内容超出可显示范围时显示滚动条并支持鼠标位置在界面内时使用滚轮进行滚动。

##### 预设切换界面

预设切换界面从左到右分两栏，分别为预设切换栏（宽度占母界面1/8）与预设展示栏（宽度占母界面7/8）。

预设切换栏有一个垂直从上到下排列的预设列表，显示预设标题，默认default，可以通过点选列表元素切换当前展示的预设。

预设展示栏从上到下分别是：标题、模型（暂时不可更改）、System Prompt。

当System Prompt内容超出可显示范围时显示滚动条并支持鼠标位置在界面内时使用滚轮进行滚动。

### 设置

设置栏大小默认1000x600px，左侧（宽度占母界面1/4，留适量边距）垂直从上到下排布设置类别，分别为“界面”、“预设”；右侧（宽度占母界面3/4，留适量边距）为设置项列表。设置项列表采用垂直从上到下布局，当超出可显示范围时显示滚动条并支持鼠标位置在界面内时使用滚轮进行滚动。

#### 界面

“界面”类别垂直从上到下排布两个子项，分别是“主页面”和“设置”。

#### 预设

暂无

## 颜色要求

### 主题要求

使用灰白配色的界面主题，标题使用加粗字体，正文使用正文字体。

### 主页面

#### 边栏

边栏所有图标背景为透明。

## 功能要求

### 核心功能

该软件通过连接Deepseek API，将输入传给Deepseek-v4-flash大模型，然后接取输出输出到输出框展示。

### 主页面

#### 边栏

##### 可操作界面图标栏

可操作界面图标栏可以通过点击未激活图标切换当前界面。

#### 可操作界面

##### 预设切换界面

预设切换界面可以切换当前使用的预设。

### 设置

#### 界面

“界面”类别的子项可以点击左侧“∨”图标或其母元素展开，展开后将其余子项向下推，并将图标改为“>”，点击“>”或其母元素收回。

“主页面”子项可以设置主页面大小（px），默认值1200x800；设置主页面标题与正文字体，默认使用系统默认字体，并读取系统已有字体，支持导入新字体。

“设置”子项可以设置设置页面大小（px），默认值1000x600；设置设置页面标题与正文字体，默认使用系统默认字体，并读取系统已有字体，支持导入新字体。

#### 预设

“预设”类别可修改预设存放的目录，默认在./Presets下。

注：暂时不要求开发模型修改功能，默认使用Deepseek-v4-flash，密钥本地保存。

## 开发规范要求

### 工具要求

使用Python语言及其工具链开发。

使用git进行版本控制。

使用Github进行远端仓库存储。

使用Github Actions搭建CI/CD。

### 分支要求

分支分为main和feature/x、develop/x、fix/x-y、release/x，默认为develop/x。main为主分支，存放目前最新的release版本。feature/x为功能分支，x为功能，负责说明当前分支主要设计的功能模块。develop/x为开发分支，x为数字，默认为1，每增加一个开发分支就+1。fix/x-y为修复分支，x为功能，y为待修复bug的说明。release/x为发布分支，x为当前发布的版本号。

### 版本号要求

版本号采用 **语义化版本号（Semantic Versioning）扩展格式**：

```
v主版本号.功能版本号.修复版本号-阶段标识.阶段版本号

示例：
v0.5.2-alpha.3
```

版本号由四部分组成：

```
vX.Y.Z-stage.N
```

其中：

- `X`：主版本号（Major Version）
- `Y`：功能版本号（Minor Version）
- `Z`：修复版本号（Patch Version）
- `stage.N`：预发布阶段及该阶段迭代次数

------

#### 1. 主版本号（Major Version）

格式：

```
vX.0.0
```

默认值：

```
v0.0.0
```

用于表示产品的重要阶段变化或架构级更新。

当发生以下情况时，主版本号增加：

- 产品进入新的稳定阶段；
- 核心架构发生重大变化；
- API、配置格式或数据结构出现不兼容修改；
- 大规模重构导致旧版本无法直接升级。

示例：

```
v0.9.5 → v1.0.0
```

表示产品从开发阶段进入第一个稳定正式版本。

```
v1.8.3 → v2.0.0
```

表示产品进行了重大升级。

------

#### 2. 功能版本号（Minor Version）

格式：

```
vX.Y.0
```

默认值：

```
v0.0.0
```

用于表示新增功能或能力扩展。

当增加新的用户可见功能时，功能版本号增加：

例如：

- 新增模型支持；
- 新增插件系统；
- 新增文件解析能力；
- 新增工作流功能；
- 新增用户交互模块。

示例：

```
v0.2.0 → v0.3.0
```

表示增加新的功能模块。

------

#### 3. 修复版本号（Patch Version）

格式：

```
vX.Y.Z
```

默认值：

```
v0.0.0
```

用于表示不改变主要功能的优化和修复。

包括：

- Bug 修复；
- 性能优化；
- UI 调整；
- 文档更新；
- 代码重构；
- 安全修复。

示例：

```
v0.3.1 → v0.3.2
```

表示功能保持不变，仅进行了优化或修复。

------

#### 4. 阶段标识（Stage）

阶段标识用于表示当前版本是否处于正式发布前。

格式：

```
-stage.N
```

例如：

```
v0.5.0-alpha.12
```

表示：

- 目标版本：0.5.0
- 当前阶段：Alpha
- 第 12 次 Alpha 构建

------

#### 阶段类型

##### dev（开发版）

格式：

```
v0.1.0-dev.1
```

表示：

项目正在开发中，功能尚未完整。

特点：

- 仅用于开发者测试；
- API 和架构可能随时变化；
- 不保证兼容性。

------

##### alpha（内部测试版）

格式：

```
v0.3.0-alpha.5
```

表示：

基础功能已经完成，可以进行内部测试。

特点：

- 功能可能缺失；
- 可能存在大量 Bug；
- 适合开发团队和早期测试人员使用。

------

##### beta（公开测试版）

格式：

```
v0.5.0-beta.2
```

表示：

主要功能已经完成，进入稳定性测试。

特点：

- 功能基本冻结；
- 重点修复问题；
- 可以开放给部分用户测试。

------

##### rc（Release Candidate，发布候选版）

格式：

```
v1.0.0-rc.1
```

表示：

该版本已经接近正式发布。

特点：

- 功能冻结；
- 仅修复严重问题；
- 若无重大 Bug，将直接成为正式版本。

------

#### 正式版本

正式版本不添加阶段标识：

```

```

表示稳定发行版本。

------

### Git Tag 规范

项目所有版本发布必须使用 **Annotated Tag（附注标签）**，禁止使用 Lightweight Tag（轻量标签）。

创建版本标签时必须使用：

```bash
git tag -a <version> -m "<message>"
```

示例：

```bash
git tag -a v1.0.0 -m "Release v1.0.0: Initial stable release"
```

推送标签：

```bash
git push origin v1.0.0
```

或推送全部标签：

```bash
git push origin --tags
```

#### Git Tag 命名规范

Tag 名称必须与版本号完全一致。

格式：

```
v主版本号.功能版本号.修复版本号-stage.次数
```

Tag 必须能够唯一对应一个版本状态。

------

#### Tag Message 说明规范

Annotated Tag 的说明信息必须包含以下内容：

```
Release <版本号>: <版本标题>

Changes:
- <变更内容1>
- <变更内容2>

Breaking Changes:
- <不兼容变更说明>

Migration:
- <升级注意事项>
```

其中：

- `Release`：固定前缀；
- `<版本号>`：必须与 Tag 名称一致；
- `<版本标题>`：简短描述本次版本目标；
- `Changes`：本版本主要变化；
- `Breaking Changes`：不兼容修改，没有则填写 `无`；
- `Migration`：升级注意事项，没有则填写 `无`。

##### 示例：功能版本发布

Tag：

```bash
git tag -a v0.3.0-beta.1 -m "
Release v0.3.0-beta.1: 多模型支持 beta

Changes:
- 增加Claude API支持
- 增加模型切换面板
- 增加模型配置管理

Breaking Changes:
- 无

Migration:
- 可兼容已有配置
"
```

#### Tag 发布流程

所有版本发布必须遵循：

**1. 确认分支**

使用：

```bash
git branch
```

确认当前分支与开发目的相符。

##### 1. 确认版本号

检查：

```bash
git status
```

确保工作区干净。


##### 2. 创建版本 Commit

例如：

```bash
git commit -m "Release v1.0.0"
```


##### 3. 创建 Annotated Tag

```bash
git tag -a v1.0.0 -m "Release v1.0.0: 首个正式版"
```


##### 4. 验证 Tag

```bash
git show v1.0.0
```

确认：

- Tag 类型为 annotated；
- Commit 正确；
- Message 完整。

##### 5. 推送 Tag

```bash
git push origin v1.0.0
```

#### Tag 删除规范

禁止直接修改已有版本 Tag。

如果 Tag 创建错误：

删除本地：

```bash
git tag -d v0.1.1-alpha.1
```

删除远程：

```bash
git push origin --delete v0.1.1-alpha.1
```

重新创建：

```bash
git tag -a v0.1.1-alpha.1 -m "..."
```

正式发布版本原则上禁止覆盖 Tag。

### GitHub Release 规范

GitHub Release 必须基于 Git Annotated Tag 创建。

Release 标题举例：

```
v1.0.0 - 首个正式版
```

Release 内容应与 Tag Message 保持一致，并可额外补充：

- 版本截图；
- Demo 地址；
- 升级指南；
- 已知问题。

## Prompt要求

新增/改动/删除任何代码前都必须stage所有新增/改动/删除文件、新增版本号（如果不确定使用哪个版本号则询问用户）并执行git commit。

当我说“撤回”时撤回到指定版本（版本号/Hash Code），如果没有提供版本或版本错误则不进行撤回并要求用户提供版本。
